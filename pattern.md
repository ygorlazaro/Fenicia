I want to implement a global design pattern for the domains.

These are the logics:

- Remove mapperly. We will use a manual mapper by calling the DTO constructors
- Remove the *Mapper.cs class and its references from the codebase
- At repository level, all the methods from abstract Repository.cs class should be protected. Only its inheritors should be able to access them. This will enforce encapsulation and prevent direct access to the repository methods from outside the repository classes.
- At repository and service levels, try the best to avoid roudtrips at the database. At the same time, try to keep the queries as lean as possible. I want to implement RESTFUL principles in our design, ensuring that each request is efficient and only retrieves the necessary data.
- Concrete repositories should implement only the necessary. Some cases will need to override the base methods to provide specific functionality, but we should avoid unnecessary overrides that could lead to code duplication or complexity. Good uses: set a default sorting, filtering, or pagination behavior that is specific to that repository's domain. Bad uses: overriding methods just to change the return type or to add minor tweaks that could be handled in the service layer.
- Repositories should not contain business logic. They should only be responsible for data access and persistence. Any business logic should be handled in the service layer, ensuring a clear separation of concerns.
- Repositories should only return primitives, nulls or their specific domain entities. They should not return DTOs or any other types that are not directly related to the data access layer. This will help maintain a clear boundary between the data access layer and the service layer, ensuring that each layer has a well-defined responsibility.
- Repositories should only depend on the data access layer and should not have any dependencies on the service layer or any other layers. This will help maintain a clear separation of concerns and prevent tight coupling between different layers of the application.
- Services should be responsible for orchestrating the business logic and coordinating between different services. Services should only be aware of their own repository and should not have direct access to other repositories. This will help maintain a clear separation of concerns and prevent tight coupling between different services.
- Services can access other services if necessary, but this should be done with caution to avoid creating circular dependencies or tight coupling between services. When accessing other services, it is important to ensure that the service being accessed is well-defined and has a clear responsibility, and that the interaction between services is well-documented and understood.
- At the services contructors, we should inject their repository as the first parameter, with the common name of "repository". This will help maintain consistency across the codebase and make it easier to understand the dependencies of each service. Any additional dependencies should be injected after the repository parameter, and their names should be descriptive of their purpose or functionality. This will help improve the readability and maintainability of the codebase, making it easier for developers to understand the relationships between different services and their dependencies.
- At services, the methods should have only one responsibility and should be named according to the action they perform. This will help maintain a clear separation of concerns and make it easier to understand the purpose of each method. Methods should avoid doing too much or having multiple responsibilities, as this can lead to confusion and make the code harder to maintain. Instead, methods should focus on a single task or action, and any additional functionality should be handled in separate methods or services. We can split them into smaller methods if necessary, but we should avoid creating methods that are too small or trivial, as this can lead to unnecessary complexity and make the code harder to read and understand.
- Put private methods at the bottom of the class. This will help improve the readability of the code by keeping the public interface of the class at the top, making it easier for developers to understand how to use the class without having to scroll through private implementation details. Private methods should be clearly separated from public methods, and their purpose should be well-documented to ensure that other developers can understand their functionality and how they fit into the overall design of the class.
- The order of methods at all the classes should be public, protected, private. Static ones first.
- All services and repositories should have interfaces into a Interfaces/ subfolder at domain level. This will help maintain a clear separation of concerns and make it easier to understand the relationships between different services and repositories. Interfaces should be named according to their purpose or functionality, and should clearly define the methods and properties that are available for use by other classes. This will help improve the maintainability of the codebase and make it easier for developers to understand how to use the services and repositories without having to dig into their implementation details.
- Register all dependencies at Program.cs level for DI.
- Controllers should only be responsible for handling HTTP requests and responses. They should not contain any business logic or data access code. Instead, they should delegate these responsibilities to the appropriate services, ensuring a clear separation of concerns and making the code easier to maintain and test.
- Controllers should return the right http status codes based on the outcome of the request. For example, a successful GET request should return a 200 OK status code, while a failed request due to invalid input should return a 400 Bad Request status code. This will help ensure that clients can easily understand the outcome of their requests and take appropriate action based on the response.
- Controllers should have xml comments for all public methods, providing clear documentation of their purpose, parameters, and return values. This will help improve the maintainability of the codebase and make it easier for developers to understand how to use the controllers without having to dig into their implementation details.
- COntrollers should have annotations for openapi/swagger documentation, providing clear and concise information about the available endpoints, their parameters, and their expected responses. This will help improve the usability of the API and make it easier for clients to understand how to interact with the application.
- All async methods should follow the naming convention of appending "Async" to the method name. This will help improve the readability of the code and make it easier for developers to understand which methods are asynchronous and which are synchronous. It will also help prevent confusion and potential bugs that could arise from calling an asynchronous method without awaiting its result.
- All async methods should have a CancellationToken parameter as the last parameter. This will help improve the responsiveness of the application and allow for better control over long-running operations. It will also help prevent potential issues with resource management and ensure that the application can gracefully handle cancellation requests from clients or other parts of the system.
- Controllers can retrieve data from token via ClaimReader class. This will help improve the security and maintainability of the codebase by centralizing the logic for reading claims from tokens, making it easier to manage and update as needed. It will also help ensure that sensitive information is handled securely and consistently across the application.
- Try to unify as much as possible the DTOs. Ideally, a single CRUD should have only a <ClassName>Request.cs and <ClassName>Response.cs. This will help improve the maintainability of the codebase and make it easier for developers to understand how to use the DTOs without having to dig into their implementation details. It will also help ensure that the DTOs are consistent and follow a clear naming convention, making it easier to identify their purpose and functionality within the application.
- If necessary, but only if necessary, we can create additional DTOs for specific use cases, but we should avoid creating unnecessary DTOs that could lead to confusion or complexity.
